# ruby-async-cicloid: local optimization campaign (Phase 2 and Phase 3 results)

Write-up of the Phase 2 campaign on `submissions/ruby-async-cicloid`, the best Ruby entry to the $12 Server Challenge (5-endpoint JSON feed API on SQLite; scored by the largest concurrent-user count that holds 5 minutes with p95 < 500 ms, p99 < 1 s and < 1 % errors on 1 vCPU / 2 GB; official score 71,000 users per the task brief, not re-verified here). Stack: Ruby 4.0.7 + YJIT + jemalloc, async/io-event io_uring, custom HTTP/1.1 with epoll-parked idle connections, extralite over a PGO-built SQLite 3.54, SQL-built JSON, fd budget with close-after-serve shedding.

Every number below is copied from `local-bench/results/*.jsonl|*.log`, the Phase 2 records `local-bench/records/impl.json` (keys `impl:<id>`, `stack:<id>`, `review:*`, `verify:final-bench`) and `local-bench/records/research.json` (local paths replaced by `<repo>`, `<scratchpad>`, `<session-root>`), or a diff of `local-bench/variants/*` against the submission; the source is named next to each table. Phase 3 numbers come from `results/stack6-*`, `stack7-*`, `final2-*`, `final2fix-*` and `knee2-*`: the `final2-*` files (11:22-12:06 local) ran the stack7 image e77fcbf98c89 under the final2 tag, the `final2fix-*` and `knee2-*` files (13:09-16:37) ran the rebuilt final2 image 6f312e85c53e (stack7 + the response-loss fix, see Phase 3), the `stack6-*` files ran facf2528f27a (`docker image inspect` Created times against the result files' mtimes); host state during Phase 3 (load averages, memory pressure, Docker VM free space, wall-clock times) is quoted from the runners' notes and marked "runner notes" where no file holds it. Deltas are (new - old) / old on `us_per_req`; negative = less server CPU per request.

Local knee (300 s hold): the baseline passes 150,000 (3 load processes) and fails 187,500 in Phase 2 and in all three Phase 3 runs (final2-knee-187500, -187500r, final2fix-knee-187500; p50 1.1-1.9 s at 96.6-97.1 % CPU). final (= stack5) and final2 both pass 187,500 every time (final: Phase 2 and final2fix-k187-1/2; final2: twice on the stack7 image, three times on 6f312e85c53e) and 230,000 (knee2-230k, 4 load processes, p99 108 / 85 ms), and both fail 280,000 (knee2-280k, 5 load processes), so the local knee of both lies between 230k and 280k (255k and 330k were not run). At 280k both servers are CPU-bound (93 % of the core) and queueing (p50 167 / 291 ms): final fails on p99 alone (1840.781 ms; p95 444.369 ms, error_rate 0.085 %); final2 fails harder (p95 1123.018, p99 3716.030 ms, error_rate 0.179 %, 4.4 % fewer requests), with its worker pool at the 4,096 `MAX_WORKERS` cap, gc_ms 21.8 s vs 13.1 s and peak memory 744 vs 559 MB. Caveats: the 230k and 280k probes are single unswapped runs with final2 on seat B, the seat favoured in every swapped pair of the day; run.sh pins each side's 4-5 load processes to two cores; the 280k loop delays (190.0 / 175.9 ms) sit just under the 200 ms exclusion limit and peak_connections reached 108k (65-70k in the clean 80k-230k runs of both phases, apart from the saturated base side of final2-knee-187500r at 76.5k), so the 280k percentiles include loadgen queueing.

Recommended result: `tdsc-cicloid:final2`, image id 6f312e85c53e (sha256:6f312e85c53e03c473734c215989ab83eca6e9fe80cb41f63975c9d47bc76649), built by `build-variant.sh` from `local-bench/variants/final2`: final + v10 churn shed-at-accept + `socket.shutdown(Socket::SHUT_WR)` after a connection's last response (http.rb only). Against final on the same day it is never worse in the swapped pairs (20k-187.5k): 20k -1.2 % (stack7 image; the fix's code path never runs at 20k), 80k -4.6 % (stack7 image: -4.3 %), 150k -6.3 % (one clean pair), 187.5k -8.0 %, sign-corrected over swapped pairs, every clean run at those loads passing; both images pass 230k and fail 280k, where final2 degrades more (knee paragraph above). It passes `test/test.sh` 42/42 (results/final2fix-test.log), used less peak memory than base in every clean Phase 3 pair (not in the excluded final2-20k-2: 194 vs 177 MB) and more than final in every fixed-image pair (+0.2 to +5.4 % up to 187.5k). The gain is in the fd-budget churn regime (80k and up, where peak_connections reaches the 65,279-descriptor budget and crosses the 65,087 shed threshold), which is where the challenge's score is decided. The shutdown fix removes the response loss the Phase 3 review found on reject paths and for pipelining clients (413 delivered 20/20 against stack7's 8/20 and 15/20), keeps stack7's two-segment saving per closed connection, and both fix reviews passed with notes (Phase 3, Response-loss fix).

What changed: five source-level edits to `app.rb`, `http.rb` and `server.rb` (sorter-free FEED SQL, a synchronous group-commit flush with a single-statement LIKE, HTTP header-walker/response/JWT trims, a LIFO worker pool that trims idle fibers, `PRAGMA mmap_size=0`), no toolchain, gem, schema or build change; `test/test.sh` passes 42/42 on the final image (verify:final-bench). final2 adds v10 to `http.rb`: newcomers accepted within 192 descriptors of the budget are served once with `Connection: close` and closed at accept time instead of being parked in epoll and closed after serving, and a connection's last response, sent with `MSG_MORE`, is followed by `socket.shutdown(Socket::SHUT_WR)`, so the FIN rides on the held segment and a later `close` with unread input no longer resets the response away (42/42 on the stack7 image, results/final2-test.log, and on 6f312e85c53e, results/final2fix-test.log).

### Metric

One JSON line per run: `requests, rps, error_rate, p50/p95/p99_ms, event_loop_delay_ms (loadgen side), peak_connections, connects, retired_connections, pass, procs, server_cpu_pct, us_per_req, server_peak_mem_mb`. `us_per_req` = delta of the server cgroup's `usage_usec` (`/sys/fs/cgroup/cpu.stat`), sampled after `RAMP + 1 s` and at the end of the hold, divided by the requests the load generator counted in that window; `server_cpu_pct` is the same delta over wall time. `pass` is the AND over load processes of the challenge thresholds. Counts are summed over processes, percentiles take the max (run.sh summary and result blocks, lines 69-82). `us_per_req` is the decision metric because the challenge's score is bounded by one core: fewer CPU microseconds per request is more users before the latency knee.

### Lens 1: rules and bytes. Verdict: pass_with_notes

Checks: `test/test.sh` 42/42 on both images via the harness; 307 raw-TCP cases byte-compared after normalising only `created_at` and health `uptime_s` (health, feed before/after writes, posts by id incl. malformed ids, unknown routes, 44 Authorization/JWT variants, header-parser variants, 40 POST bodies, like paths, pipelining, split heads and bodies, byte-by-byte requests, two concurrent bursts with 38 read-backs, 12 pipelined creates in one ms); sha256 of `install.sh start.sh build.sh Gemfile Gemfile.lock epoll.rb sqlite_train.c` identical in both images; no `sysctl`, `/proc/sys`, `somaxconn`, `nice`, `chrt`, `taskset` in the stack5 image (only `ulimit -Sn` in start.sh and a comment in http.rb); pragmas keep `journal_mode=WAL` and `synchronous=NORMAL`; a live stack5 container has a non-empty `/tmp/feed.db-wal` and WAL header bytes; `sqlite_master` identical to `seed/feed.db` (9 objects); `authenticate()` recomputes and `crypto_verify_32`-compares the HMAC on every request (only the secret-derived keyed state is pre-built); no response or row cache; read-after-write cases identical to base.

### Why the half-close leak was left alone

- It is in the baseline image (99 of 100 sockets leaked vs 84 of 100 on stack5), so it is not a regression of this campaign; the review's remit was to verify the final build, and both proposed fixes change the dispatch path (event-mask plumbing through `epoll.rb`, or an extra syscall on every request), which would need its own 42/42 run and swapped pairs before it could be kept under the Phase 2 rules.
- The challenge's scored load (keep-alive HTTP clients) and `test/test.sh` do not half-close; the robustness review's own 10,000-request keep-alive run, 2,261 connect/close cycles, 50 RST clients and 500 slowloris heads left no leaked sockets. The finding is carried forward to Phase 3.

### Response-loss fix (final2 = stack7 + shutdown)

Finding (Phase 3 robustness review, table below): stack7's `write(socket, data, last = true)` sends a connection's last response with `MSG_MORE` and `disconnect` then `close`s; with request bytes still unread on the socket, Linux `tcp_close()` sends RST and drops the corked segment, so a client streaming an oversized body (413 / 431 / 400) or pipelining sees only ECONNRESET. Fix, the only code change from `variants/stack7`: `socket.shutdown(Socket::SHUT_WR)` right after the last MSG_MORE send, which raises the FIN while the segment is still queued, so the response leaves with the FIN in one segment and the later `close` has nothing to discard; the `SHED_TIMEOUT` comment now says it bounds each read or write wait, not the connection (`diff -u variants/stack7/http.rb variants/final2/http.rb`). Built as `tdsc-cicloid:final2` = 6f312e85c53e; `tdsc-cicloid:stack7` stays e77fcbf98c89; 42/42 (results/final2fix-test.log). ## Limitations

- Slot bias. The two server seats are not equivalent: A/A pairs read +0.3 % in one window (aa20k) and -6.5 % in another (stack2-aa); v05, v10, v11, v12 and the stack2 series all show the sign following the seat, and on the Phase 3 day seat B read 4.5-7 % lower in the four stack6/stack7 20k pairs (stack6-p1/p2, stack7-p1/p2: B vs A -5.5 / -7.0 / -7.1 / -4.5 %), the two final2-vs-base 20k pairs (final2-20k-1/2r) differ by 9.4 points in the same direction, and the two 80k stack7 deltas are about 6 points apart (stack7-c1r vs c2); in the afternoon the variant's delta was 1.6-4.3 points more negative with the variant on seat B (final2fix-c1 / c2 -6.5 / -2.6 %, final2fix-k187-1 / -2 -8.8 / -7.2 %, stack6-c1 / c2r -1.6 / +2.7 %). Every delta quoted here comes from swapped pairs, but a single 20k pair still carries several points of noise; the 20k final-vs-base spread (-29.6 % / -22.1 %) is the baseline's own drift (73.9 -> 69.7 us), the Phase 3 20k spread (-28.5 % / -19.1 %) the same effect. Sub-1 % effects (v02, v11, v12) cannot be resolved on this host; stack7's 20k mean (-1.2 %) and stack6's 20k / 80k means (+1.0 / +0.5 %) are inside that band; the claims are the means at 80k and above (stack7 -4.3 % at 80k; final2 -4.6 / -6.3 / -8.0 % at 80k / 150k / 187.5k).
- Platform. The harness is Docker Desktop on this Mac (the apt mirror in the build errors is `ports.ubuntu.com/ubuntu-ports`, the arm64 archive), the challenge runs an x86 VPS; `install.sh` adds `-march=native` only when `uname -m` is x86_64, so the local arm64 images are generic builds of the same source. Absolute us/req, the latency knee and the 65,535-descriptor ceiling do not transfer; only relative deltas measured on the same host at the same time are claimed. The load generator is `connection_load.c`, not the challenge's k6 script; its own `event_loop_delay_ms` was 33.7-116.8 ms during the Phase 2 knee holds (27.4-35.0 ms at 80k) and 17-190 ms in the clean Phase 3 pairs, so loadgen-side jitter is in the recorded latencies and Phase 3 percentiles are a little higher for both sides of every pair.
- Loadgen-bound runs. Phase 3 shows what a host under memory pressure does to this harness: loop delays of 0.2-37 s, error rates of 2-4 %, peak_connections well above the 65-69k of clean Phase 3 runs up to 230k (77k at 80k, 125-133k at 150k), both images failing identically (stack7-c1, stack7-k150-1), one side alone failing on latency with both sides at 1.2-5x their clean us/req (final2-20k-2: the final2 side; final2-80k-2: the base side) or inflated percentiles with the verdict unchanged (final2-knee-187500). Such a run says nothing about the server and is excluded; the threshold used is about 200 ms of loop delay. run.sh gives each pair side two load cores whatever `--procs` is: on the quiet afternoon host 230k with 4 processes stayed at 23-29 ms and 280k with 5 reached 176-190 ms (under the threshold and counted, but marginal), while the 150k pairs final2fix-k150-1 / -1r read 344-663 ms with all four sides passing (excluded; k150-2 read 57-82 ms).
- Host speed varies between sessions: in the Phase 3 morning block at 80k both base (50.0-52.3 vs 40.7-41.2 us/req) and final2 on the stack7 image (36.0-37.1 vs final's 29.5-30.7) read about 17-29 % higher than in Phase 2, and at 187.5k base read 6-10 % higher (58.6-60.7 vs 55.1); in the afternoon block stack5 was back at Phase 2's level (29.9-30.7 at 80k apart from stack6-c2r's 33.9, 31.9-32.0 vs 32.5 at 187.5k) while base still read about 9-20 % higher at 80k (44.7-48.9) and 1.6 % lower at 187.5k (54.2); at 20k the morning readings are at or below Phase 2's (base 57.2-71.0 vs 69.7-73.9, final2 46.3-50.8 vs final 52.0-54.3). Relative deltas agree at every load; cross-session absolute comparisons are not made.
- Disk blocker. The Docker VM disk hit 0 bytes free during Phase 2: v07 (PGO Ruby) was never built, stack6 failed to build twice and was built only later; v07 additionally needs a single-layer build because `local-bench/Dockerfile` copies only `install.sh` and `sqlite_train.c*` into the toolchain layer. In Phase 3 the VM (128 GiB `Docker.raw`, shared with the user's other containers) fell under the 1.5 GB floor for about 25 minutes and the following runs were skipped rather than risk the shared disk: stack7-k150-1r, stack7-k187-1/2, stack6-c1/c2, knee2-230k and its follow-ups (runner notes). The afternoon block ran them with the VM at 11.0-11.3 GB free: stack6-c1/c2/c2r, the 150k and 187.5k pairs on the fixed image in place of stack7 (final2fix-k150-*, final2fix-k187-*), knee2-230k and knee2-280k.
- Not measured: the knee between 230k and 280k and above 280k (230k / 280k are single unswapped runs, and every 187,500 final2-vs-base run had the baseline on A); the fixed image at 20k and the `shutdown(2)` cost in isolation; stack6 above 80k; 80k pairs for stack1 and stack3 (not required by the rules for non-churn steps); a dedicated test asserting the group-commit batch size after v06's direct scheduler pushes (stack:v06); any run with the challenge's own k6 client.
- Recorded-but-uncertain magnitudes: v05's standalone -3.93 % rests on the seat-penalty explanation (variant-first pairs alone are about 0 %); v09's stack step (-7.53 % at 20k) is larger than its standalone -1.84 %; stack:v04's `mean_delta_80k = 0` and the other zeros in impl.json are placeholders for pairs that were not run, not measurements; the stack6 Phase 3 input's `mean_delta_80k = 0` likewise means not measured.
- Memory: final peak container memory is 3-5 % higher than base at 80k with two load processes (483-495 vs 469-473 MB) and lower at every other load; final2 is below base in every clean Phase 3 pair (186-205 vs 209-210 MB at 20k, 452-511 vs 496-546 at 80k, 571-608 vs 717-734 at 187.5k; 651 vs 800 in the loadgen-bound final2-knee-187500; above it only in the excluded final2-20k-2, 194 vs 177). Against stack5 the fixed image peaks higher in every pair: +0.2 to +5.4 % up to 187.5k (483 / 462, 486 / 461, 540 / 539, 590 / 560, 581 / 563 MB), +11.6 % at 230k (656 / 588) and +33 % at 280k (744 / 559, pool at the worker cap); the stack7 image was above stack5 in two of the four clean stack7-vs-stack5 pairs (+4.1 % at 20k p2, 205 vs 197; +5.3 % at 80k c1r, 496 vs 471; below in p1 and c2, 202 vs 205 and 468 vs 485) and in both excluded runs (649 vs 613 at 80k c1, 852 vs 782 at 150k).
- Known behaviour left in the final and final2: the half-close CLOSE_WAIT leak, the 17 KB head slack and the ghost-user 500 (all pre-existing, see Review findings), plus the one intentional divergence (bare CR inside a header value -> 400). The MSG_MORE response loss found in the stack7 image is fixed in final2 6f312e85c53e (Response-loss fix). final2 keeps the per-read rather than per-connection `SHED_TIMEOUT` (now documented as such), the submission README's stale description of the close policy (see Phase 3 review findings), an `/app/README.md` inside the image that still reads `IMAGE_ID_PLACEHOLDER`, an RST-cut response when one larger than the send window is closed with unread input (as on stack5), and one extra `shutdown(2)` per closed connection whose CPU cost no pair isolates; it sends 8.00 segments per one-shot connection against stack5's 10.00 (response and FIN coalesced), and fails 280k harder than final (pool at the 4,096 worker cap).
